日期：2026-10-01
目标：把 P2「知识能提升存活率」从模拟器推进到**真实目标检测**链路。

## 结论（先说结果）

**真实 YOLO 推理链路已跑通，但离可用还很远。**

- ✅ 真实截图 → 真实权重（yolov8n.pt）→ 真实检测 → 项目感知契约 JSON，全程无 mock
- ✅ 端到端能输出合法 JSON，stderr 干净
- ❌ COCO 权重**不认识游戏实体**，检测不到外星人 / BOSS / 花瓣
- ❌ 单帧 ~2.4s，比游戏要求的 0.5s/帧 慢约 5 倍

## 踩到的两个坑

### 1. pip 装 torch 被 OOM 静默杀掉

症状：日志在 `Installing collected packages: torch` 处**直接截断**，
没有报错、没有回溯。装完 `import torch` 才报
`libtorch_global_deps.so: cannot open shared object file`。

真因不是磁盘满（当时还有 5.3G 空闲），而是**内存**：pip 解压 196MB 的
whl 需要较大内存，本机只剩 254MiB，进程被内核 OOM killer 干掉。

解法：`pip install --no-deps torch`（依赖稍后单独装），
把解压的内存峰值压下去，一次成功。

**教训**：日志截断 + 无回溯 = 被信号杀死，不是 pip 自己的 bug。
遇到这种要先看内存，别盯着磁盘。

### 2. `RuntimeError: operator torchvision::nms does not exist`

ultralytics 从 PyPI 拉的 torchvision 是 GPU 版，
和 `--index-url .../whl/cpu` 装的 CPU 版 torch 对不上。

解法：单独从 CPU 源装 torchvision：

```bash
pip install --force-reinstall --no-deps torchvision \
  --index-url https://download.pytorch.org/whl/cpu
```

## 未解决问题（诚实清单）

1. **缺游戏专用权重**。对 florr 这类游戏，需要针对该游戏标注训练的数据集
   与权重，或者换成通用但可用的方案（模板匹配 / 颜色分割 / 找连通域）。
   这是 P2 落地的**主要缺口**，不是调参能解决的。
2. **性能差 4.4 倍**。截图就占 1538ms —— 这是 X11 传全屏 PNG 的开销，
   比 YOLO 本身还大。优化方向：截子区域、降分辨率、或改用 GPU。

## 追加：截图 1538ms 的根因（不是传输，是 Wayland 合成器）

上面把「优化截图」列为下一步，实测后结论是：**在这台机器上 1.6s 是地板，改代码解决不了。**

### 根因：GNOME on Wayland + rootless Xwayland

```
XDG_SESSION_TYPE=wayland    XDG_CURRENT_DESKTOP=GNOME
Xwayland :0 -rootless -noreset ...
```

`-rootless` 意味着 X 的 root 窗口**不是真实屏幕**，只是一个合成占位。
所以所有走 X11 的抓屏工具全部失效：

| 工具 | 结果 | 原因 |
|---|---|---|
| `import -window root` | `BadMatch` | rootless 下无真实 root 窗口 |
| `xwd -root` | `BadMatch` | 同上 |
| `mss` 10.2.0 | `XProtoError` opcode 73 | XFIXES 枚举显示器时崩（构造函数就挂，连显式区域都传不进去） |
| `gnome-screenshot` | **✓ 1573ms** | 唯一能走通的：经 Mutter 合成器 D-Bus portal |

### 关键反直觉发现：成本与像素量无关

| 区域 | 像素占比 | 中位耗时 |
|---|---|---|
| 1366×768 全屏 | 100% | 1802 ms |
| 1024×576 | 56% | 1918 ms |
| 683×384 | 25% | 1557 ms |
| 341×192 | 6% | 1810 ms |

**25% 的像素不比 100% 慢** —— 传输和编码都不是瓶颈，是合成器侧的固定开销。
这也否掉了「截子区域」这个本来最想做的优化方向。

进程启动也不是瓶颈：`gnome-screenshot --version` 只要 **45ms**，
真正抓屏 1651ms。改 flag 也无效：

| 命令 | 中位 |
|---|---|
| `gnome-screenshot`（全屏） | 1573 ms |
| `gnome-screenshot -w`（当前窗口） | 1772 ms |

### Pillow 的 ImageGrab 是个陷阱

`PIL.ImageGrab.grab()` 测出 1791ms，看着像独立实现。查源码发现
它内部就 `subprocess` 调 `gnome-screenshot`（源码里 `gnome-screenshot`、
`subprocess` 都有，`xcb` 没有）—— 测的是同一个东西，别误以为换库能提速。

### 两条真正的出路

1. **换回 Xorg 会话**（`/etc/gdm3/custom.conf` 设 `WaylandEnable=false`，重启）
   → X11 抓屏恢复，mss/import 几十毫秒。代价：要 sudo + 重启 + 改变用户整个桌面。
2. **florr 是网页游戏，绕开合成器**：用已装的
   `/home/g-bill/chrome/opt/google/chrome/chrome`（注意不在 PATH）起浏览器，
   经 CDP `Page.captureScreenshot` 抓 canvas，或直接在页面里
   `readPixels`/`toDataURL` 取像素。这条路对网页游戏最直接，也最快。

结论：**不要再优化截图代码**，瓶颈在桌面会话类型，不在 UGF。

## 追加二：CDP 方案实测（快 9~23 倍，但被 Cloudflare 挡住）

按上面第 2 条出路实测 Chrome CDP 抓帧。

### 机制可行，速度显著

| 方式 | 中位耗时 |
|---|---|
| `gnome-screenshot`（Mutter 合成器） | 1573 ms |
| CDP `Page.captureScreenshot`（本地 canvas 页） | **168 ms** |
| CDP `Page.captureScreenshot`（空白页） | **68 ms** |

即 **9~23 倍** 提速，且 `canvas.getImageData()` 直读像素也可用。
**机制本身没问题。**

### 但 florr.io 抓不到

三层都堵住了：

1. `curl https://florr.io/` → **HTTP 403**（Cloudflare 拦非浏览器 UA）
2. headless Chrome 加载 florr.io → **渲染进程卡死**：
   `Runtime.evaluate` 25s 超时，`Page.captureScreenshot` 只回 2546 字节空白帧。
   加 `--disable-gpu --use-angle=swiftshader` 也一样。
3. headed Chrome → 在本环境**起不来调试端口**
   （注意：新版 Chrome 报 `DevTools remote debugging requires a
   non-default data directory`，必须加 `--user-data-dir`；
   但加上之后 headed 模式在本机仍然没有调试端口，headless 则正常）

### 踩坑记录

- `/json/new` 新版 Chrome 只接受 **PUT**，GET 返回的不是页面 target。
- **别在 `/json/new` 的 URL 里直接填目标站**：页面重载会阻塞握手。
  要先建 `about:blank`、连上 WS，再 `Page.navigate`。
- `Page.navigate` 的响应在页面重载时可能永不返回 —— 发了不等，
  后续用 `Runtime.evaluate` 探活。给每条命令加超时，否则整个脚本挂死。

### 结论修正

CDP 是**机制上最优**，但它对 florr **不解题** —— Cloudflare 挡在前面。
反过来，**换 Xorg 会话能同时解决 florr**：X11 下可以直接抓浏览器窗口
（绕开与站点程序的任何交互），约 50ms，且不受 Cloudflare 影响。

所以两条路的真实排序（针对 florr）：

| 方案 | 速度 | 能否抓 florr | 代价 |
|---|---|---|---|
| CDP headless | 68~168ms | **✗ Cloudflare + 渲染卡死** | 无 |
| 换 Xorg 会话 | ~50ms | **✓** | sudo + 重启 + 换桌面环境 |
| 维持现状 | 1573ms | ✓ | 无 |

**本轮没有改动 UGF 主代码** —— 探针脚本都在 /tmp，已清理。

## 追加三：选定方案 —— 换 Xorg 会话（对所有游戏通用）

用户明确要求「不只是 florr，是所有游戏」。据此选定换 Xorg 会话。

### 为什么这是通用解，而不是给某个游戏打补丁

当前的限制是**全局**的：GNOME on Wayland + Xwayland `-rootless`，
X 的 root 窗口不是真实屏幕。这个坑对**所有**游戏一视同仁 ——
原生客户端、网页游戏、模拟器都受影响，且都无法靠 UGF 代码绕过
（已验证：区域截取无加速、PIL.ImageGrab 内部就是 gnome-screenshot）。

换 Xorg 后 X11 抓屏恢复（约 50ms），**新增游戏档案时不必再考虑抓屏来源**。
CDP 方案虽然机制上更快（68~168ms），但只对「我们自己控制的浏览器页面」有效，
且被 Cloudflare 挡住 florr，因此不作为通用方案。

### 切换前已验证的前置条件

| 检查项 | 结果 |
|---|---|
| `/usr/share/xsessions/gnome-xorg.desktop` | ✓ 存在 |
| `xserver-xorg-core` | ✓ 2:21.1-1.3+deb13u4 |
| `xserver-xorg-input-all` | ✓ 1:7.7+24+deb3u1 |
| `gdm3` | ✓ 48.0-2，当前 display-manager |
| `WaylandEnable` 现状 | 未显式设置（默认启用） |

任一项缺失都会导致无法登录图形界面，因此脚本会在写入前逐项复查，缺失即中止。

### 脚本（`tools/xorg_switch/`）

- `switch_to_xorg.sh` —— 复查前置条件 → 备份 `custom.conf` → 写
  `WaylandEnable=false` → 验证。**不自动重启**，由用户决定时机。
  编辑逻辑在样例文件上验证过：写入 `[daemon]` 段内、注释与其他段完整保留、
  重复执行不重复插入（幂等）。
- `rollback_xorg.sh` —— 恢复带时间戳的备份，需交互确认。
- `verify_xorg_capture.sh` —— 重启后对比实测：会话类型、`import`/`xwd`/`mss`
  可用性与延迟、端到端每帧耗时。
- `README.md` —— 重启后的操作步骤与回滚三种方式。

### 安全网

1. GDM 登录界面右下角齿轮可切回 "GNOME on Wayland"（不需要命令行）
2. `rollback_xorg.sh` 恢复备份
3. 黑屏进不去 → `Ctrl+Alt+F2` 切 tty，root 登录后 `cp` 备份再重启

### 尚未进行

- `perception_server._SCREENSHOT_CANDIDATES` 的优先级调整（等重启后实测数据）
  当前顺序是 `gnome-screenshot → scrot → import → maim`，
  切换后应把 `import` 提到最前，`gnome-screenshot` 降为兜底。

## 追加四：v1 切换脚本失败复盘（我的三个错误）

用户重启后跑验证脚本，结果 `XDG_SESSION_TYPE = wayland`，切换**完全没生效**。
排查发现 v1 脚本有三个错误，都在真实机器上暴露：

### 错误 1：配置文件名错了（致命）

GDM 48（本机版本）用的是 **`/etc/gdm3/daemon.conf`**，不是 `/etc/gdm3/custom.conf`。
后者在本机**根本不存在**。

v1 脚本第一件事就是 `sudo cp -a "$CONF" "$BAK"` —— 源文件不存在，
在 `set -euo pipefail` 下**直接中断**，一个字节都没改。

**我之前为什么没发现**：诊断时用了
`cat /etc/gdm3/custom.conf | grep -vE "^\s*#|^\s*$"`，`cat` 失败后 grep 收到空输入、
什么都没输出，而 `||` 分支也没触发。我把「什么都没打印」误读成
「文件存在但没有 WaylandEnable 键」，据此写下「未显式设置（默认启用）」。

**教训**：判断配置项是否存在的正确做法是显式检查文件是否存在并读回内容，
不能把「命令无输出」当成「配置项缺失」。

### 错误 2：没查自动登录，导致安全网是假的

`/etc/gdm3/daemon.conf` 里 `AutomaticLoginEnable=True` + `AutomaticLogin=g-bill`。
自动登录**不显示会话选择器**，所以我上一轮反复强调的
「万一不行，在登录界面用齿轮切回 GNOME on Wayland」这条退路**根本不存在**。

**教训**：给出「怎么退回」的建议前，必须先确认退回所需的界面/入口是否存在。

### 错误 3：拿不可比的数据下结论

用户重启 7 分钟后测得端到端 7103 ms（切换前 2400 ms），一度看起来是性能退化 3 倍。
实际是机器刚开机、负载 8.10、可用内存仅 631MB（4 个 `/app/api` python 进程
约 950MB + opencode 桌面版 400MB）。**这个数据不可与低负载基线比较。**

已把这个检查写进 `verify_xorg_capture.sh` 第 0 段：负载 >4 或可用内存 <800MB
时直接提示「数据不可比」。

### 修正内容

- 配置文件定位改为 `daemon.conf` 优先、回落 `custom.conf`（兼容新旧 GDM）
- 识别**已注释掉**的 `#WaylandEnable=false` 并就地取消注释，而不是盲目插入
- 默认 `--safe`：临时关自动登录，保留会话选择器作为真实可用的退路
- `--restore-autologin` / `--rollback` / `--check` / `--force` 子命令
- 验证脚本压掉 cv2 的 C++ NNPACK 日志（上一版刷了 100 多行把结果全淹了）
- 编辑逻辑在 `daemon.conf` 副本上验证：注释行识别正确、幂等（重复跑不重复插入）

## 追加五：切到 Xorg 成功，抓屏提速 7 倍（通用，所有游戏生效）

### 切换结果

```
XDG_SESSION_TYPE = x11        ✓
gnome-screenshot 2303 ms
import           1443 ms      （Wayland 时 BadMatch 失败）
xwd               201 ms      （Wayland 时 BadMatch 失败）
mss                15 ms      （Wayland 时 XProtoError 崩溃）min 10 ms
```

`mss` 相比 Wayland 基线 1573 ms **快 100 倍**。
换 Xorg 后 X11 抓屏能力**对所有游戏恢复**——原生客户端、网页游戏一视同仁，
以后新增游戏档案不必再考虑抓屏来源。

### 据此重排了候选顺序

`_SCREENSHOT_CANDIDATES` 原来是 `gnome-screenshot → scrot → import → maim`。
那个顺序是**在 Wayland 下定的**，当时 gnome-screenshot 是唯一能用的
（其余全部 BadMatch / XProtoError）。换到 Xorg 后它变成了最慢的那个，
顺序不改的话每帧都在用最贵的工具。

新顺序（按实测延迟）：

```python
_SCREENSHOT_CANDIDATES = ("mss", "xwd", "import",
                          "gnome-screenshot", "scrot", "maim")
```

新增 `_screenshot_with_mss()`：mss 不是命令行程序，走纯库路径（无子进程）。
异常一律吞掉返回 False，好让 Wayland 等场景能回落到后面的候选。

### 效果

| | Wayland | Xorg + 新顺序 |
|---|---|---|
| `_take_screenshot` | 1573 ms | **219 ms** |

分解：mss 抓取 32ms + PNG 编码 122ms = 154ms（探测含开销 219ms）。
**PNG 编码现在是抓取本身的 4 倍**——下一步可以省掉：把原始像素直接喂
YOLO 的 `numpy` 输入，不落盘。这是当前剩下的最大单点优化。

### 改掉的 3 个环境依赖测试

本轮 4 个失败里，3 个是我改动暴露出的**测试环境依赖**问题，
和上一轮 `test_headless_report` 同一类：

1. `test_candidate_order_prefers_gnome_over_import` —— 焊死了
   "gnome-screenshot 必须在 import 前面"，这是 Wayland 时期的机器状态。
   已改名 `test_candidate_order_is_speed_ranked_not_session_hardcoded`，
   改为断言「最快的排第一 + 各会话的兜底工具都在列表里」，
   并在 docstring 里记下这个顺序被推翻过两次、每次的原因。
2. `test_screenshot_tool_is_probed_not_merely_present` ——
   断言 `calls[0] == "gnome-screenshot"` 同样是写死顺序；
   改为断言「从第一个候选开始试」+「试了不止一个」。
3. `test_ops.py::test_strict_promotes_warn_to_error` ——
   跑子进程看退出码，等于假设「本机一定有 WARN」。现在 WARN 数是 0
   （Xorg + 装了权重，环境真的健康了），strict 自然返回 0。
   改为直接给 `_check()` 注入 WARN，验证 strict 判定逻辑本身。

**教训（第二次撞上同一类问题）**：断言机器环境状态 = 埋雷。
本轮之前已有一次同样教训（`test_headless_report`），
说明「测试要 hermetic」这条规则还没落实到位。三个测试都改成
不依赖环境当前状态、只验证被测逻辑本身。

第 4 个失败 `test_longrun` 是已知的资源竞争偶发（单独跑通过），非本轮改动。

## 追加六：发现并修掉「每帧重载权重」—— http 感知链路其实从未真正工作过

上一节把抓屏从 1573ms 降到 219ms 后，我去测真实链路
（`build_perception_payload("http")`），发现一个比抓屏严重得多的问题。

### 症状

```
_run_yolo 第1次: 8175 ms   backend=None  detections=None
_run_yolo 第2次: 8073 ms   backend=None  detections=None
返回: {"_timeout": true}
```

**每帧 8.1 秒，且返回超时 —— 一个检测结果都产不出来。**

### 根因

`_run_yolo()` 每帧起一个子进程跑 `detect.py`，而 `detect.py` 每次执行都要
`import ultralytics` + `YOLO(weight)` **重新加载权重**（冷启动实测 8~14 秒），
正好撞上 `config.yaml` 里的 `perception.yolo_timeout: 8`。

所以：**整条 http 感知链路从上线到现在一直是「每帧超时、零结果」**。
之前几轮报告的「YOLO 跑通了」全部来自进程内直调
（`m.predict(...)`），没有走真实链路，所以没暴露这个问题。

这提醒了一件事：**验证必须打穿真实调用路径**，进程内直调只能证明
「模型能推理」，不能证明「系统能跑」。

### 修法：模型常驻 + 原始像素直喂

新增快路径，在 `build_perception_payload` 里优先走：

```
mss 抓原始像素 → numpy(BGR) → 常驻模型 predict → 不落盘、不起子进程
```

- `_YOLO` 字典缓存模型，全局只加载一次
- `_capture_array()` 取 mss 原始像素并转 BGR
  （mss 给 RGB，ultralytics 内部按 BCHW 排布，通道错了颜色模型会退化）
- 任何一环失败**自动回落**到旧的「落盘 + 子进程」路径，并在跳过原因里
  附上快路径的错误便于定位
- `_silence_cpp()` 在 fd 层压制 cv2 的 C++ 日志

### 正确性验证

快路径（BGR 数组）与文件路径（PNG，由 ultralytics 自行解码）必须给出一致结果：

```
快路径(BGR)   detections=1  laptop conf=0.522
文件路径(PNG) detections=1  laptop conf=0.520
像素抽查(0,0): 快路径BGR=[78,44,37]  真实RGB=[37,44,78]   ← 翻转正确
```

### 效果

| | 旧路径 | 新路径 |
|---|---|---|
| 每帧耗时 | ~8200 ms | **703 ms**（min 486） |
| 结果 | **每帧超时，零产出** | 真实产出检测 |
| 首帧 | — | 19.3s（含模型加载，只一次） |

从「完全不可用」变成「可用」，且提速 12 倍。

### 顺带修掉一个自己引入的 bug

`test_yolo_model_cached_across_calls` 抓到我在 `_yolo_predict` 里把模型加载了
**两次**（`_silence_cpp(YOLO, weight)` 写了两遍，第二行才是赋值）。
这会让 19 秒的冷启动直接翻倍。这个 bug 是新写的测试抓出来的 ——
测试在修 bug 这件事上是有用的。

### 测试

1046 passed（新增 6 个快路径测试：快路径生效、不落盘不起子进程、
失败回落、双路失败时原因含快路径错误、mss 不可用返回 None、模型只加载一次）。

原有 8 个 http 测试因快路径抢跑而失败（表现为 `KeyError: '_skipped'`）——
它们 mock 的是兜底路径。已在公共 helper `_patch_http` 里统一关掉快路径，
让它们继续测本该测的东西；快路径由新测试单独覆盖。
