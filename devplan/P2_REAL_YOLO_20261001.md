# P2 · 真实 YOLO 权重落地记录

日期：2026-10-01
目标：把 P2「知识能提升存活率」从模拟器推进到**真实目标检测**链路。

## 结论（先说结果）

**真实 YOLO 推理链路已跑通，但离可用还很远。**

- ✅ 真实截图 → 真实权重（yolov8n.pt）→ 真实检测 → 项目感知契约 JSON，全程无 mock
- ✅ 端到端能输出合法 JSON，stderr 干净
- ❌ COCO 权重**不认识游戏实体**，检测不到外星人 / BOSS / 花瓣
- ❌ 单帧 ~2.4s，比游戏要求的 0.5s/帧 慢约 5 倍

## 踩到的两个坑

### 1. pip 装 torch 被 OOM 静默杀掉

症状：日志在 `Installing collected packages: torch` 处**直接截断**，
没有报错、没有回溯。装完 `import torch` 才报
`libtorch_global_deps.so: cannot open shared object file`。

真因不是磁盘满（当时还有 5.3G 空闲），而是**内存**：pip 解压 196MB 的
whl 需要较大内存，本机只剩 254MiB，进程被内核 OOM killer 干掉。

解法：`pip install --no-deps torch`（依赖稍后单独装），
把解压的内存峰值压下去，一次成功。

**教训**：日志截断 + 无回溯 = 被信号杀死，不是 pip 自己的 bug。
遇到这种要先看内存，别盯着磁盘。

### 2. `RuntimeError: operator torchvision::nms does not exist`

ultralytics 从 PyPI 拉的 torchvision 是 GPU 版，
和 `--index-url .../whl/cpu` 装的 CPU 版 torch 对不上。

解法：单独从 CPU 源装 torchvision：

```bash
pip install --force-reinstall --no-deps torchvision \
  --index-url https://download.pytorch.org/whl/cpu
```

## 检测结果（诚实记录）

真实截图 1366×768 上跑 yolov8n.pt：

```
detections: 1
  coco_class=laptop  conf=0.737  bbox=(4,0)-(1361,768)
```

即：它把**整块屏幕识别成了一台 laptop**。这是在真实桌面上拍的，
不是游戏画面。

这条结果只能证明一件事：**真实权重 + 真实截图 + 真实推理的管道是通的**。
它**不**证明「YOLO 能检测游戏实体」—— 恰恰说明 COCO 权重不行。

`player` 字段带了 `_fallback: true`，明确标注「没识别到人，用了兜底坐标」，

## 未解决问题（诚实清单）

1. **缺游戏专用权重**。对 florr 这类游戏，需要针对该游戏标注训练的数据集
   与权重，或者换成通用但可用的方案（模板匹配 / 颜色分割 / 找连通域）。
   这是 P2 落地的**主要缺口**，不是调参能解决的。
2. **性能差 4.4 倍**。截图就占 1538ms —— 这是 X11 传全屏 PNG 的开销，
   比 YOLO 本身还大。优化方向：截子区域、降分辨率、或改用 GPU。
   本机无独显，CPU 路线到此为止。
3. **COCO 类别映射的稀有度是 unknown**。战斗评估按稀有度算威胁分，
   这里不敢编 —— 编错会得出错误决策。

## 追加：截图 1538ms 的根因（不是传输，是 Wayland 合成器）

上面把「优化截图」列为下一步，实测后结论是：**在这台机器上 1.6s 是地板，改代码解决不了。**

### 根因：GNOME on Wayland + rootless Xwayland

```
XDG_SESSION_TYPE=wayland    XDG_CURRENT_DESKTOP=GNOME
Xwayland :0 -rootless -noreset ...
```

`-rootless` 意味着 X 的 root 窗口**不是真实屏幕**，只是一个合成占位。
所以所有走 X11 的抓屏工具全部失效：

| 工具 | 结果 | 原因 |
|---|---|---|
| `import -window root` | `BadMatch` | rootless 下无真实 root 窗口 |
| `xwd -root` | `BadMatch` | 同上 |
| `mss` 10.2.0 | `XProtoError` opcode 73 | XFIXES 枚举显示器时崩（构造函数就挂，连显式区域都传不进去） |
| `gnome-screenshot` | **✓ 1573ms** | 唯一能走通的：经 Mutter 合成器 D-Bus portal |

### 关键反直觉发现：成本与像素量无关

| 区域 | 像素占比 | 中位耗时 |
|---|---|---|
| 1366×768 全屏 | 100% | 1802 ms |
| 1024×576 | 56% | 1918 ms |
| 683×384 | 25% | 1557 ms |
| 341×192 | 6% | 1810 ms |

**25% 的像素不比 100% 慢** —— 传输和编码都不是瓶颈，是合成器侧的固定开销。
这也否掉了「截子区域」这个本来最想做的优化方向。

进程启动也不是瓶颈：`gnome-screenshot --version` 只要 **45ms**，
真正抓屏 1651ms。改 flag 也无效：

| 命令 | 中位 |
|---|---|
| `gnome-screenshot`（全屏） | 1573 ms |
| `gnome-screenshot -w`（当前窗口） | 1772 ms |

### Pillow 的 ImageGrab 是个陷阱

`PIL.ImageGrab.grab()` 测出 1791ms，看着像独立实现。查源码发现
它内部就 `subprocess` 调 `gnome-screenshot`（源码里 `gnome-screenshot`、
`subprocess` 都有，`xcb` 没有）—— 测的是同一个东西，别误以为换库能提速。

### 两条真正的出路

1. **换回 Xorg 会话**（`/etc/gdm3/custom.conf` 设 `WaylandEnable=false`，重启）
   → X11 抓屏恢复，mss/import 几十毫秒。代价：要 sudo + 重启 + 改变用户整个桌面。
2. **florr 是网页游戏，绕开合成器**：用已装的
   `/home/g-bill/chrome/opt/google/chrome/chrome`（注意不在 PATH）起浏览器，
   经 CDP `Page.captureScreenshot` 抓 canvas，或直接在页面里
   `readPixels`/`toDataURL` 取像素。这条路对网页游戏最直接，也最快。

结论：**不要再优化截图代码**，瓶颈在桌面会话类型，不在 UGF。
