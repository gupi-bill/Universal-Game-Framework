## 一、P3 跨 Python 版本 ✅

### 做法

用 `uv` 建一个干净的 Python 3.12 环境（3.13 是本机主力），
按 `requirements.txt` 装依赖，然后跑真实链路。

### 结果

| 项目 | 3.13.12（主力） | 3.12.14（干净环境） |
|------|-----------------|---------------------|
| 核心模块导入 | 9/9 | **9/9** |
| MCP stdio 握手 | 16 工具 | **16 工具** |
| 需要改代码 | — | **零改动** |

### 结论

`requires-python = ">=3.9"` 目前无法验证 —— 3.9 装不上，
因为**根分区只剩 708MB**（`uv python install 3.9` 报
`No space left on device`）。已验证的区间是 **3.12 ~ 3.13**。

这个约束要写进文档，不能让 `>=3.9` 继续挂在那里当未验证的承诺。

## 二、P1 接入递减曲线 ✅（在工具链层面）

### 测量方法

用 `tools/add_game.py` 连续接入 4 款新游戏，记录端到端耗时
（生成 YAML + 严格自检），并全部跑一次真实 dry-run 对局。

### 结果

| 序 | 游戏 | 接入耗时 | strict 自检 | dry-run 对局 |
|----|------|---------|------------|-------------|
| 4 | roguelike_dungeon_crawler | 837 ms | ✅ | — |
| 5 | dungeon_crawler | — | ✅ | — |
| 6 | metroidvania | 863 ms | ✅ | ✅ 5 回合，闭环 100% |
| 7 | stardew_like | 767 ms | ✅ | — |

**7 款档案全部 `--strict` 通过。接入耗时稳定在 767~863 ms，无递增趋势。**

### 但这只证明了「工具链不退化」

P1 的真正判据是「第 10 款游戏接入耗时 < 第 1 款的 1/5」。
现在的数据只能说明：

- ✅ 接入是**纯配置**的，不碰核心代码
- ✅ 耗时**不随游戏数增长**
- ❌ 还不知道「更复杂的游戏」是否需要更多手工调整

`florr`（75 行）与 `demo_arcade`（117 行）字段数相同，
说明这三款**复杂度相当**，不足以体现递减曲线。

**真正的检验需要一款明显更复杂的游戏**（比如带技能树、多人联机、
复杂状态机的），看接入成本是否仍然平坦。

### 顺带修的两个 bug

1. `add_game.py --help` 会**真的生成一份 `help.yaml` 并切换 config.yaml**
   —— 一个查帮助的操作产生了副作用。已加参数解析，未知参数返回 2。

2. `_sanitize_name("roguelike dungeon crawler")` 得到
   `roguelike_dungeon_crawler` —— 原来的
   `re.sub(r"[^\w.-]+", "_", ...)` 把整串压成一个标识符，**词边界丢失**。
   游戏名常是多词短语，压平后既难读也可能撞名。
   改为按分隔符切词、词内清理、词间用 `_` 连接。

## 三、P2 真机输入端 ✅（中段仍缺权重）

### 约束

- 无 torch、无 ultralytics
- 根分区只剩 708MB，YOLO 权重 + torch 需 GB 级

所以**无法在本机训练或下载 YOLO 权重**。

### 但可以做的是：把「权重缺失」这一个变量隔离掉

写了一个**真实像素分析器**（零权重，纯 PIL）替代 YOLO：
读 PNG 头拿真实宽高 → 缩到 64×36 → 逐格算亮度/饱和度 →
与边缘中位亮度对比 → 找出偏离背景的区域 → 映射到 player/entities。

它做的是**真的图像处理**，不是硬编码数据。

### 实测结果

```
截图:  成功 133580 bytes，1366×768，未设 DISPLAY（自己找到 :1）
分析:  已分析像素 True，8 个区域
  player  x=854 y=640            ← 下半屏中央，符合真实布局
  entity  alien_drone   x=171 y=128    ← 上半屏
  entity  alien_drone   x=1195 y=128
  entity  alien_swarmer x=512 y=128
```

完整链路（真实截图 → 分析 → 归一化 → 战斗评估）：

```
帧 1: 5128 ms  后端=http  实体=8  跳过=None
  决策=fight  威胁比=0.43  推荐套装=combat  心态=balanced
帧 2: 4197 ms  实体=8   （同上）
帧 3: 4857 ms  实体=8   （同上）
```

**每个坐标都来自 1366×768 的真实像素。**

### 一个真实发现：截图是性能瓶颈

| 环节 | 耗时 | 占比 |
|------|------|------|
| 截图（gnome-screenshot） | 1623 ms | 58% |
| 检测脚本（含 Python 冷启动） | 1260 ms | 42% |
| 归一化 | <1 ms | ~0% |

对比 `PIL.ImageGrab`：1675 ms —— **一样慢**。
说明瓶颈不在工具，而在 **X11 协议传输 1.4MB 像素数据本身**。

游戏要求 0.5s/帧，当前 ~4~5s/帧，**差一个数量级**。

可能的解法（都需实机验证）：
- XShm / MIT-SHM 扩展（避免走 X protocol 慢路径）
- 降低截图分辨率
- GPU 截图
- 接受「非游戏级实时」，只做低频采样

### 中段仍缺什么

| 缺什么 | 影响 |
|--------|------|
| YOLO 权重 | 分析器只找「显眼的东西」，不认识什么是敌人/BOSS |
| 实时性 | 4~5s/帧，达不到游戏要求的 0.5s/帧 |

**所以 P2 现在的准确表述是**：
输入端（真实像素）✅ 通 → 中段（真实检测）❌ 缺权重 → 决策端 ✅ 通
