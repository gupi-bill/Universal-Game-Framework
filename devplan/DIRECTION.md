# Universal-Game-Framework · 定位与发展方向判断

> 制定时间：2026-09-21 21:30 ｜ 依据：本轮实测（S1~S9，614 用例全绿）+ 源码与档案实读，而非 README 措辞

---

## 一、它到底是什么

一句话：**一个把「任意 2D 网页游戏」接进 AI 智能体、并让智能体越打越强的通用框架。**

拆开看，它由四层构成：

| 层 | 组成 | 现状 |
|---|---|---|
| 感知层 | `perception_server.py`（YOLO/HTTP/mock 三后端） | S6 已离线化，可无显卡跑 |
| 决策层 | `predictor.py`（运动预判）+ `combat_judge.py`（威胁评估/心态/套装）+ LLM 兜底规则 | S3/S4 已单测覆盖，数学部分可靠 |
| 执行层 | `mcp_server.py`（15 工具）+ `game_action`（拟人键鼠） | S9 已逐个验证可调用；真实键鼠在本机不可测 |
| 记忆层 | `knowledge_md/` MD 知识库 + `kb_maintainer` + `session` + `report_notifier` | S5/S7/S9 已验证读写与往返，但**库是空的** |

**真正值钱的资产不是「会打 Florr」，而是两件事：**
1. **接入契约**：一款游戏 = 一份 YAML 档案，核心零改动。这是「通用」的全部含义。
2. **进化闭环**：实战 → 复盘 → 知识入库 → 下次决策引用。这是「越打越强」的全部含义。

---

## 二、现在最真实的短板（实测结论，不是猜测）

1. **「通用」尚未被证明**。已有两份档案：`florr.yaml`（依赖实机：Windows + 真窗口 + 第三方 YOLO + 云端 VLM，本机一条都跑不了）与 `space_invaders.yaml`（字段残缺的占位：无套装、无战术、无端口、威胁分级自相矛盾）。**两款游戏都没有在本机端到端跑通过一轮**——架构上通用 ≠ 实证上通用。
2. **知识闭环从未真正转过一圈**。知识库为空，视频学习依赖 VLM 与联网，检索命中率指标没有一次真实采样。
3. **没有可复制的「接入新游戏」路径**。`tools/add_game.py` 能生成档案，但「生成 → 校验 → 冒烟 → 试跑 → 出报告」这条链没有被端到端验证过，新人接一款游戏实际上靠猜。
4. **入口分裂**：`admin_panel` / `ui_tkinter` / `ui_streamlit` / `ui_pyqt` 四套前端并存，使用者不知道该开哪个。
5. **合规风险未澄清**：README 只有一句免责，未说明框架应定位于「本地 / 授权环境的技术研究与自建游戏适配」。

## 三、我（开发方）该往哪推 —— 优先级排序

排序原则：**可验证性 × 杠杆价值**。本机无实机、无密钥，凡依赖真机/真 VLM 的工作都无法验收，一律后置。

| 优先级 | 方向 | 理由 |
|---|---|---|
| **P0** | **第二款游戏端到端跑通**（space_invaders：补档案 → mock 感知 → 全链路 → e2e 测试） | 这是「通用框架」唯一的证明方式；跑通第二款，第三款的成本才趋近于零 |
| **P0** | **接入流程产品化**（模板档案 + 向导 + 校验 + 冒烟 + 一键试跑 + 文档） | 把「接一款游戏」从几小时压到 30 分钟，框架的真正卖点才能兑现 |
| **P1** | **知识闭环实证**（seed 知识 → 检索命中 → 决策引用 → 复盘写回 → 命中率指标） | 「越打越强」目前只是文档措辞，需要一次可复现的闭环实证 |
| **P1** | **可观测与门禁**（测试门禁脚本、启动自检、大盘真实反映运行模式） | 决定这个项目能不能被别人接手继续做 |
| **P2** | 稳定性长跑 / 资源占用门禁 / 安全加固（路径穿越、档案沙箱、密钥） | 长期运行与分发的前置条件 |
| **P3** | 打包分发（.deb / 便携版 / EXE / APK） | 已有脚手架但从未实证构建产物可用 |
| **P4** | **Florr 深度拟人化（原 v2.0 主题）** | 依赖实机与真 VLM，本机不可验证；在 P0~P2 完成前投入等于无法验收的猜测性开发 |

**一句话路线**：先把「第二款游戏跑通 + 接入流程产品化」做实，把框架从「文档上通用」变成「实证上通用」；Florr 深度化留到地基之后。

## 四、未来用它的人该往哪走 —— 三类用户的上手路径

### A. 想让 AI 代打某款游戏的人
1. 备环境：Python venv + 感知后端（真机用 YOLO，无显卡用 `UGF_PERCEPTION_BACKEND=mock`）+ `.env` 填 LLM/VLM。
2. 选档案：`agent_cli.py -c validate <game>` 确认档案合法。
3. **先在 mock / dry-run 下跑通链路，再上真机**——这是本框架推荐的唯一正确顺序，能避免 80% 的"跑起来什么都不动"问题。
4. 开跑：`brief` → `play`，用监控大盘看状态与预判。

### B. 想把自己的游戏接进来的人
1. 写一份 `game_profiles/<name>.yaml`：实体分类 / 威胁分 / 稀有度 / 套装 / 战术 / 感知端口。
2. `validate` 自检 → mock 感知冒烟 → 试跑 → 出报告。
3. **契约：全程不改核心代码**。这条必须用自动化测试锁死，是框架对使用者最重要的承诺。

### C. 想二次开发的人
1. 对外被调：用 `mcp_server.py` 的 15 个工具；对内主动调：用 `mcp_connector.py` 连外部 MCP。
2. 新增能力优先写成 `skills/<name>/SKILL.md` + `skill.py`（技能包），**不要往核心里塞逻辑**。
3. 新增判定阈值一律走 `config.yaml`，不要硬编码。

### 合规边界（必须写进文档）
本框架面向**本地 / 自建 / 已授权环境**的智能体技术研究与游戏适配。在他人运营的在线服务器（如 florr.io 官方服）运行自动化程序违反其服务条款并可能导致封号，框架不鼓励、不提供绕过手段。

## 五、本次判断对开发计划的直接影响

- 剩余 S10~S14（游戏档案 / UI 收敛 / 运维脚本 / 测试门禁 / 验收归档）**按原计划收尾**，它们是地基的最后五块砖。
- 之后进入第二阶段工作表（`PLAN_PHASE2.md`，S15~S26），主题依次是：**第二款游戏端到端 → 接入流程产品化 → 知识闭环实证 → 稳定性与安全 → 打包分发 → 文档与发布**。
- Florr 深度化不在本轮窗口内，作为后续实机阶段单独立项。
